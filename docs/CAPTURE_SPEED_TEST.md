# 촬영 속도 비교 시험

촬영 화면의 **진단 정보 → 촬영 속도 비교 시험** 또는 앱 URL의 `?benchmark=1`로 연다.
개발 중에는 `npm run dev`로 실행한다. 갤럭시 Samsung Internet 실기기 카메라 시험에는 HTTPS 배포 URL이 필요하다.

1. 카메라를 시작하고 평소처럼 라벨을 촬영하거나 JPEG 파일을 선택한다.
2. **5회 속도 비교**를 누른다. 같은 입력 파일을 각 방식에 사용한다.
3. 처리·저장·ZIP 생성 시간의 중앙값과 저장 픽셀 수, 파일 크기를 확인한다.
4. 두 ZIP을 저장하고 PC에서 글자, 바코드, 사진 방향을 비교한다. 측정 결과는 JSON으로 저장할 수 있다.

## 측정 방법

- 기존 방식: `createImageBitmap`으로 디코딩 → 기존 앱의 공통 canvas/JPEG 인코더(4096px, 품질 0.96).
- 원본 우선: JPEG 헤더에서 크기·EXIF 방향을 확인하고 조건을 만족하면 바이트를 그대로 저장한다.
- EXIF 방향 1~8은 원본 JPEG와 함께 보존한다. 4096px 초과 또는 확인할 수 없는 메타데이터만 기존 변환으로 처리한다. 이 경우 결과에 사유가 표시된다.
- 방식별 전체 경로를 한 번 준비 실행하고 제외한다. 이후 각 5회를 번갈아 실행해 순서 영향을 줄인다.
- 사진 획득은 한 번만 한다. 비교 중에는 미리보기를 중지한다. 촬영·사용자 다운로드·화면 갱신·시험 데이터 삭제 시간은 측정에 포함하지 않는다.
- 저장 시간에는 기존 앱과 같은 IndexedDB 연결과 트랜잭션 완료 대기를 포함한다.
- ZIP 시간에는 저장소 재조회와 사진 1장, manifest 2개를 묶는 시간을 포함한다. 전체는 사진 처리 시작부터 ZIP 생성 완료까지의 경과 시간이다.
- 한 장의 처리 및 내보내기 비교다. 여러 장이 누적된 세션이나 실제 다음 촬영 버튼 간격을 직접 측정한 값은 아니다.

## 데이터와 호환성

- 실제 촬영 DB와 별개인 `box-label-capture-speed-test` DB를 사용하고 실행별 레코드는 완료·실패 시 삭제한다.
- 기존 촬영·공유·ZIP 경로는 유지한다. 시험 화면은 기존 인코더와 저장·ZIP 함수를 재사용한다.
- 시험 ZIP도 `{sessionId}/cart_001/cart_001_box_01.jpg`, `manifest.json`, `manifest.csv` 구조이며 JPEG를 ZIP에서 재압축하지 않는다.
- 파일을 원본 저장해도 기존 경로 규칙, JPEG MIME, 크기·용량 메타데이터를 유지한다.
- 일반 촬영은 원본 우선 저장을 기본으로 사용한다. 원래 촬영 화면에서 바로 촬영하면 적용된다. 진단 정보의 최근 촬영 저장 방식에서 실제 적용 여부를 확인할 수 있다.
- PC 측정값은 갤럭시의 실제 성능으로 해석하지 않는다. Samsung Internet에서 동일 시험을 실행한 JSON으로 판단한다.

## EXIF를 보존하는 원본 저장

세로 촬영의 EXIF 회전·반전 정보 때문에 원본 저장이 적용되지 않던 조건을 제거했다. JPEG 바이트와 EXIF 태그는 수정하지 않고, 미리보기는 이미지의 방향 정보를 반영한다. `image_width`와 `image_height`는 방향을 반영한 표시 크기이며, 방향 5~8은 가로·세로 축을 바꾼다. IndexedDB의 `originalWidth`와 `originalHeight`에는 파일에 인코딩된 픽셀 크기를 유지한다.

JSON manifest에 `exif_orientation`을 추가하고 CSV의 마지막 열에도 같은 값을 추가한다. 이전 열의 위치와 사진 경로는 유지한다. 기존에 변환 저장한 사진과 이전 저장 데이터는 방향 1로 취급한다. 재촬영으로 방향이 달라지면 해당 사진의 방향 정보도 갱신한다.

ZIP의 JPEG도 EXIF를 포함한 원본 파일이다. PC에서 읽을 때에는 파일의 EXIF 방향을 한 번 반영해야 한다. 예를 들어 Pillow에서는 `ImageOps.exif_transpose(Image.open(path))`를 사용한다. 이미 EXIF를 적용한 디코더의 결과에 다시 회전하면 안 된다. 외부 OCR 프로그램의 방향 처리 여부는 이 저장소만으로 확인할 수 없다.

참고: [브라우저 image-orientation](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/image-orientation), [Pillow EXIF 방향 반영](https://pillow.readthedocs.io/en/stable/reference/ImageOps.html#PIL.ImageOps.exif_transpose).

## PC 시험 결과 (2026-11-17)

Windows의 Headless Edge 157.0.4341.60에서 프로덕션 빌드를 실행했다. 입력은 재현 가능한 질감·라벨 패턴을 그린 4032×3024 JPEG(3,418,845바이트, EXIF 방향 1)이며, 실제 휴대폰 카메라 사진이 아니다. 방식별 준비 실행 1회 후 각 5회 중앙값이다.

| 항목 | 기존 변환 | 원본 우선 |
| --- | ---: | ---: |
| 사진 처리 | 197.0 ms | 1.2 ms |
| IndexedDB 저장 | 1.5 ms | 1.5 ms |
| 사진 1장 ZIP 생성 | 22.6 ms | 22.4 ms |
| 처리 시작 → ZIP 준비 완료 | 221.2 ms | 25.6 ms |
| 저장 픽셀 수 | 4032×3024 | 4032×3024 |
| JPEG 크기 | 3,424,573 바이트 | 3,418,845 바이트 |

이 입력에서는 전체 경과 시간이 약 88.4% 줄었고, 차이는 주로 재변환 생략에서 발생했다. 실제 셔터 응답이나 삼성 인터넷의 다음 촬영 버튼 간격에 대한 측정은 아니다.

위 PC 시험 당시 검증: 두 ZIP의 CRC, JPEG와 두 manifest 경로·크기 메타데이터를 확인했다. 원본 우선 ZIP의 JPEG는 입력과 바이트까지 동일했다. 당시 EXIF 방향 6은 기존 변환으로 처리했으나 현재는 원본 보존으로 변경했다. 4096px 초과 입력의 축소와 기존 촬영·재촬영·카메라 전환·새로고침 복원·ZIP 다운로드, 280~1366px 화면을 검증했다.
